# 统一开发与维护规范

版本：2.0｜生效日期：2026-11-16｜适用：本项目代码、数据库、接口、任务、测试与发布。

本文替换原有开发规范。具体代码写法见[代码书写规范](代码书写规范.md)，注释细则见[注释规范](注释规范.md)，AI执行入口见项目根目录[AGENTS.md](../AGENTS.md)。业务规则以用户最新确认及对应领域文档为依据；未经确认，维护、重构和格式化不得改变业务行为。

## 1. 使用方式与规则强度

- **必须**：组织隔离、权限、状态与配额一致性、接口契约、敏感信息保护、数据库兼容性、验证与可回滚发布。
- **新增及实质改写代码执行**：命名、排版、类型说明、模块职责、注释。只改一行文案，不要求顺便整理整文件。
- **建议**：函数超过约60行、模块超过约800行时评估拆分；数字是评审信号，不是强制拆分任务。禁止为凑行数增加无意义包装。
- 历史代码按本次需求涉及范围逐步整理。格式化、重命名、模块拆分与业务变更分别处理；禁止借维护任务全仓重写。

## 2. 当前架构和修改入口

当前为Python标准库HTTP服务、原生JavaScript/CSS、SQLite WAL；Python依赖见requirements.txt，前端DOM测试依赖见package.json。不要根据文件名或早期README推断为完整生产架构。

| 模块 | 当前职责 | 修改约定 |
|---|---|---|
| server.py | HTTP路由、会话、CSRF、输入输出、静态文件及调度启动 | 新业务规则放领域模块；历史路由中的SQL逐步迁出，不顺带大改 |
| domain.py / Platform | 领域入口、事务、权限、分发账本及通用查询 | 优先复用现有事务和方法；新独立领域可提取协作者，不要求所有模块都做Mixin |
| distribution.py | 共享匹配规则、采购主体项目、自动分发与汇总 | 手动、自动、预览、实际创建、总览不得各写一套资格规则 |
| synced_demands.py | 原表需求到可执行需求的映射 | 不覆盖已发送交付快照；区分每日与项目总量 |
| demand_sync.py / qq_sheet.py | 同步编排 / 腾讯文档读取解析 | 原表身份、完整性验证失败保持已有业务数据；外部编号不重造 |
| media_vehicles.py | 每媒体车型库与同步管理 | 媒体字典隔离，版本、拉取结果可追溯，不用名称猜ID |
| yiche.py / yiche_transport.py | 易车字段及直连协议 | 与乙方协议分离，不能混用返回码含义 |
| zhemanhui.py / zhemanhui_integration.py | 软米协议 / 分发和回调业务整合 | 协议负责报文；集成层负责持久化、幂等和账本 |
| excel_intake.py | 表格读取与格式兼容 | 导入和手工/API录入复用业务校验，不能只靠模板必填 |
| security.py | 加密、口令、签名、HMAC指纹 | 不另造算法，不把密钥写进源码 |
| static/app.js / style.css | 页面、交互、统一请求与样式 | 沿用render、api、data-action，按需抽渲染片段 |
| migrations / tests / docs | 数据演进 / 验证 / 规则与发布证据 | 变更时更新对应内容，不维护不可核实的固定用例数 |

依赖方向为HTTP入口→领域/任务编排→协议与数据访问。外部HTTP实际发送必须在数据库写事务提交后进行；领域编排可以调用适配器，但不能在长事务内等待网络。新增运行时配置在入口加载、校验并传入；已有环境开关保持兼容，不额外散落到页面或规则函数中。

## 3. 不得破坏的业务不变量

1. 每次读写按org_id限制组织范围；对象查询同时检查id和组织。租户唯一键、回调关联和外部来源配置也必须带组织语义。
2. 合作主体、接收方、最终媒体是不同概念。乙方转发不能算两笔售卖；会员和KA是同一主体下独立项目。
3. 外部需求编号来自媒体或原表。系统内部id与外部编号分开，字符串前导零不得丢失；需求编号与城市、车系一起映射到对方字段。
4. 线索、历史售卖、分发交付、发送尝试和回调事件分别建模。一笔交付重试不新增售卖次数、配额或收入。
5. 售卖上限、KA限制、去重窗口等从现有配置读取。默认值不代表合同或行业规则，不得把2次、30天等重新硬编码到分支中。
6. 匹配预览不锁定库存；创建时重新校验并原子预占。可匹配数量按线索去重，不等于可创建分发笔数，也不保证整个候选集合都能同时占到配额。
7. 配额只经账本方法更新，交付状态、需求计数与quota_ledger必须一致。取消、失败、有效、冲正都要有唯一事件键及审计依据。
8. 每日量按北京时间自然日计算；项目总量按项目周期累计。已结束或原表已移除需求不参与新分发，保留历史。
9. 接收成功、乙方存储、最终媒体入库、最终有效分开记录。结果未知保留UNKNOWN，不按成功或失败猜测，也不盲目重发。
10. 真实媒体、乙方转报和本地模拟分别标记证据来源。测试探针不能混入正常库存、有效量、结算和业务配额。
11. 字段权限同时覆盖列表、详情、搜索、筛选选项、导出及原始快照。前端隐藏不等于授权。
12. 总览“当前可匹配线索”复用匹配页资格逻辑；“累计入库”与“待匹配”不能混名。统计口径变更需同步标签、接口、文档和测试。

具体规则入口：[分发规则](分发规则使用与验收.md)、[匹配池](匹配线索池说明.md)、[同步说明](腾讯文档项目同步说明.md)、[总览口径](运营总览统计口径.md)、[软米接口](软米乙方接口对接说明.md)。文档与实际不一致时先核实，不能用过时文档覆盖当前已确认行为。

## 4. 编码与命名

### Python

新模块使用4空格、单行一条语句、导入分标准库/第三方/本项目三组；以120字符为可读性目标，长URL和必要数据字面量可例外。禁止新增星号导入和无说明的宽泛except。

文件和函数snake_case，类PascalCase，常量UPPER_SNAKE_CASE。用actor、conn、lead、demand、delivery、route、response表达业务含义；不要把不同记录都叫data或d。循环索引i可用；兼容旧调用时不为改名而修改全部调用链。actor也可以是受控系统任务或回调身份，不一概当作已登录用户。

新公共接口优先类型注解，复杂输入可用小型dataclass或明确字段字典。不要只为减少参数数量把有约束的参数变成任意dict。返回结构有稳定定义，不让成功和失败随意换类型。

### JavaScript与CSS

新增独立前端文件使用2空格；局部修改既有文件不做全量缩进转换。变量/函数camelCase，类PascalCase，DOM id和data-action沿用中划线。沿用现有视图路由id，不为统一大小写破坏链接。

请求优先走api()。文件下载、外部授权跳转等需要特殊传输时，写明原因并保留错误处理。api()目前没有自动向用户展示所有request_id，需排障时显式保留，不可在文档声称已有。

用户与外部数据进入HTML字符串必须esc()；URL编码用URL/URLSearchParams/encodeURIComponent，URL协议和目标另行校验。不要把esc()当作URL或脚本验证。使用事件委托和data-action，不新增内联onclick。复用样式类和CSS变量，避免依赖表格第几列的全局选择器。

页面状态按领域归属维护；新复杂状态集中管理，不与既有模块级状态重复保存。异步页面请求防止旧响应覆盖新页面；操作后保留合理筛选与分页。列表支持20/50/100，筛选应由后端最终执行。

## 5. 数据库、事务和迁移

- 当前业务时间主要是带UTC偏移的ISO 8601文本，由now()/later()/parse()处理；会话有效期等少量字段为epoch秒。新增字段必须声明类型、单位和时区，不能把全库改成时间戳。展示与每日配额用Asia/Shanghai。
- 金额为整数分，边界接收元时精确转换，不用浮点累计。数量为非负整数，需求目标为正整数。
- 内部主键沿用uid()。外部编号单独存储并使用业务唯一约束，不把行号作为外部需求主键。
- 使用参数化SQL；表名/列名若动态拼接必须来自固定白名单，不能接收用户原始字符串。
- 已发布迁移不可编辑。当前本地已登记到029（028及029未发布），下一次仍先核对目录和线上schema_version再分配新编号；新增迁移同时登记Platform._migrate()和schema_version。
- 当前加载器按分号拆分SQL，靠schema_version保证成功迁移不重复执行。并非要求每条语句都IF NOT EXISTS；ALTER TABLE也应只执行一次。不要在SQL字符串/注释中插入分号，不引入依赖内部分号的trigger/executescript块，除非先单独升级加载器并验证兼容性。
- 写事务复用tx()的BEGIN IMMEDIATE，事务内失败应整体回滚。不把同一业务拆到多个互不关联的提交；异步补偿必须持久化、可重试且幂等。
- 数据修复与结构迁移分开：带dry-run、范围、修复前后数量、重复执行策略、审计与备份。禁止在功能启动时顺便清空或重建业务数据。
- 未发送任务可依规则取消；已发送请求和需求/路由快照保留历史，不能用当前配置重解释旧交付。

## 6. API、外部适配与回调

内部API沿用/api/v1、统一code/data/message/request_id响应和Fault错误处理。错误码表达稳定机器语义，中文提示面向操作人员；已有泛化错误码分批细化，避免为改名破坏调用方。

内部会话写请求检查CSRF；开放API与回调按各自协议鉴权，不能要求乙方带登录CSRF。后端始终独立校验权限、必填、数值和字段归属。

每个适配器文档必须列出：来源和核对日期、对方字段与本地字段、鉴权、HTTP方法与编码、测试/正式地址、超时、返回码、幂等/查询能力、回调关联与确认响应、字典来源、启用条件和未验证项。不能把示例Token当作账号凭证，也不能照抄示例渠道号覆盖正文确认值。

请求出站使用固定或受控目标；设置超时、响应大小限制，禁止携带客户数据跟随未经验证的重定向。GET报文含手机号、姓名时，应用/代理/错误日志不得记录完整查询串或请求URL。

发送流程：规则校验→原子持久化交付及预占→提交→唯一任务领取/记录发送状态→事务外网络请求→独立事务记录结果。发送超时只表示结果未知；没有对方幂等或查单依据不得自动重试。

回调流程：解析及限制参数→验证签名或每笔随机令牌→精确定位交付及组织→持久化结果/事件→原子更新账本与状态→提交后确认接收。同结果重复回调返回成功且不重复记账；矛盾结果记录冲突，不静默覆盖；持久化失败不能返回成功。

协议不支持签名时应记录限制；使用现有每笔随机令牌、摘要存储、恒定时间比较和HTTPS。不能凭“来源于某个IP”替代关联与鉴权。

软米专用语义：supid=6且无需Token；errorCode=1是乙方接收成功；只有resultCode=0且code=2001才有效，其余失败，原因取Code码管理。易车直连接口的同名code可能含义不同，不能混用。

## 7. 权限与敏感信息

个人明文、密钥、Cookie、CSRF、回调令牌和完整报文不能写入注释、报告、测试快照、Git或控制台。手机号检索用现有Vault.fingerprint()的带组织HMAC；普通digest(phone)不能替代抗枚举指纹。

密文沿用Vault，密钥与业务数据分开管理；日志使用内部ID、业务错误码和脱敏字段。备份保护数据库、解密密钥与撤回删除清单的恢复关系，禁止把data目录打进代码交付包。

明文查看按权限、用途和审计控制；导出按申请/双人审批规则；不要擅自把所有查看、撤回、删除都改成双人流程。新增权限同时维护PERMS、后端、前端展示及测试。

## 8. 测试与可复现验证

新增或改变业务规则、跨系统状态、数据库迁移、鉴权时必须有对应测试；纯文案或说明调整不机械增加测试。断言最终状态、错误码、配额及记录数量，避免只断言HTTP200或重复实现内部代码。

普通自动化测试只使用TemporaryDirectory等隔离数据库和虚构数据、模拟传输。不要连接仓库data目录或线上服务。真实联调与自动回归分开，需用户授权范围、目标、次数和记录；自动测试绝不能因为环境变量残留而真实发线索。

从项目根目录执行（使用安装好requirements.txt的Python 3.11+；实际可执行路径按环境配置）：

```sh
python3 -m unittest discover -s tests -p 'test_zhemanhui*.py' -v
python3 -m unittest discover -s tests -p 'test_dashboard_overview.py' -v
python3 -m unittest discover -s tests -p 'test_*.py' -v
node --check static/app.js
```

先跑改动相关用例；涉及共享规则/状态/权限/数据库时跑全量Python回归。需要本地监听的测试应在允许回环网络的环境执行，环境限制与代码失败分开记录。

UI测试需先看对应.cjs脚本的端口、fixture、启动和数据假设，不能把过时脚本直接指向线上。tests/prelaunch_fixture.py支持隔离HTTP测试，jsdom测试需Node及package.json中的依赖；不要默认npm test存在。DOM测试不等于真实浏览器排版验收。

业务适配至少覆盖：正确请求、缺失字段、错误ID、超时/非JSON、接收成功仍待判定、有效/无效回调、错误令牌、重复与矛盾回调、回调先于发送响应、组织隔离和配额幂等。新增迁移验证旧版数据库升级、重启不重执行及外键检查。

报告记录执行命令、版本或文件哈希、隔离范围、时间、通过/失败/跳过与未验证项；不要用旧测试数量证明新版本。通过后只有新变更、失败或未解决风险才需要扩大/重复验证。

## 9. 发布、备份与回滚

### GitHub同步与上线边界

用户确认采用：完成修改并测试 → 提交及推送GitHub开发分支 → 汇报检查结果 → 等用户明确安排上线。每个完整功能或修复形成可审阅提交，长任务可每天推送进度分支；不按每次保存文件或固定每小时提交。开发分支使用codex/前缀，经Pull Request审查合并main，不自动合并、不强推。

推送前检查远端是否更新、暂存文件是否仅属于本任务、是否含业务数据及凭证。遇到冲突或推送被拒绝，先核对差异，不用reset --hard或强推覆盖其他工作。未完成任务留在开发分支，并如实说明。

GitHub检查只执行隔离自动化测试、JS语法及补丁格式检查，不配置生产凭证、不拉取生产数据库、不触发部署。CI配置存在并不等于主分支保护已经生效；仓库管理员仍需按套餐能力设置必须经过PR及检查通过。审批和保护设置未经核实不能声称已开启。

正式上线单独选择确定提交或不可变版本标签，发布同一份已验收代码。测试环境与生产环境分开，业务数据和环境配置独立保留；禁止用本地data覆盖生产。首次接入GitHub不扩大既有真实联调或上线授权。当前没有自动上线工作流，后续如需发布按钮再按明确要求实施。

当前已核实环境：/www/wwwroot/saas.asoapple.cn/leadsys；systemd carlead.service；Apache反代；Python /www/server/carlead/venv/bin/python；127.0.0.1:8765；域名https://saas.asoapple.cn。这些是环境事实，不是源码常量，发布前必须重新核对。不要复用本机admin演示账号操作线上或把本机data覆盖线上。

每次发布按顺序：

1. 明确修改、目标环境、外部发送范围。核对线上源码与本地差异、服务参数及schema_version，识别别人已上线的修改。
2. 完成隔离测试；准备仅含代码/迁移的文件清单、原文件和新文件SHA-256及发布说明。与线上基线不一致就停止覆盖，先合并。
3. 在服务器私有暂存目录上传，校验哈希、语法、依赖和迁移兼容性。备份受影响代码和加密数据库，记录可用密钥/删除清单恢复位置；报告不展示密钥。
4. 根据迁移兼容性安排维护窗口，必要时暂停任务领取/新写入。定向替换文件并重启carlead.service，不无故重启Apache或其他站点。
5. 核验systemd active、/health、已授权账号核心操作、回调错误鉴权、任务调度及实际外发开关。/health当前external_sending主要反映易车直连，不能单靠它证明所有乙方通道均关闭；还要检查ZMH配置、环境开关及路由。
6. 记录发布文件、备份位置、验证证据、是否真实联调和仍关闭的能力。单条探针授权不能扩大为批量或真实客户推送。

回滚以恢复兼容的前一版代码为首选。新增表一般保留；不执行删除新表作为日常回滚。若旧代码不兼容新结构，必须有已验证的兼容方案。数据库恢复会丢失备份后数据，须另行明确授权、停止写入并对账；不能把“替换代码+恢复旧数据库”当作无损回滚。

## 10. 文档、变更记录与逐步改造

每次交付说明：改了什么、为什么、影响哪些页面/表/接口、如何验证、是否已发布、哪些未完成。改业务字段同步表格模板、API映射、字段权限、详情、筛选和导出；改指标同步口径和展示。

变更记录见[CHANGELOG.md](CHANGELOG.md)，条目只写已核实内容。重大选择另加docs/decisions/YYYY-MM-DD-主题.md，说明背景、决定、替代方案、兼容与撤销条件；不为小文案建决策文档。

建议推进顺序：先稳定规范及测试→按实际修改范围展开压缩代码和命名→提取重复规则与领域模块→拆分前端视图→再评估更严格的格式/类型工具。每步有独立证据，不把全面格式化或迁移技术栈设为新增功能的前置条件。

格式化工具若引入，先确定版本与配置，预览范围并独立提交。当前没有统一black/ruff基线，不能声称全仓已通过；禁止直接运行black .或ruff --fix全仓制造不可审阅的变更。

## 11. 交付前检查

- 规则、命名及注释与当前实现/用户确认一致，没有虚构合同、字段、索引或测试结果。
- 无跨组织读写、越权字段泄露、明文凭证或客户信息进入日志。
- 手动/自动/预览/提交/报表共用规则，账本与回调幂等有证据。
- 迁移只新增、历史快照保留、普通测试不读写业务库或触发外发。
- 外部状态未知保持未知；接收成功不冒充最终有效。
- 新增/修改代码已运行适当检查，失败和未验证项已明确。
- 发布有线上基线、备份、兼容回滚、健康和业务验证；启用范围未超出授权。
