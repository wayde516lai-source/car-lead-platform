# 统一注释规范

版本：2.0｜生效日期：2026-11-16｜配套：[开发规范](开发规范.md)、[代码书写规范](代码书写规范.md)。

目标：下一位维护人员能判断一段代码为何存在、修改会影响什么、边界在哪里。注释是可核实的维护说明，不能替代清晰命名、校验、测试或领域文档。

## 1. 写什么、不写什么

必须解释：业务约束的原因、外部协议的特殊含义、事务和网络边界、幂等键、未知结果与冲突处理、兼容旧数据的理由。算法确实难读时解释过程；单位、时区、编码、外部ID归属不明显时写清。

不要给每行赋值、循环、普通查询写同义复述。删除失效注释与注释掉的死代码；无法核实的历史依据写“待确认”，不能编造合同条款、PRD章节、负责人、索引或生效日期。简单私有函数命名已充分表达时不强制长docstring。

新增模块和公共业务接口应有说明；改动旧方法时同步修正有关注释，不要求全仓补齐。以中文描述业务，保留英文代码字段、错误码及对方原始术语；同一份注释避免中英文重复整段。

## 2. 模块与类说明

新模块顶部docstring交代职责、主要依赖和边界；写当前已经实现的内容，不写将来愿景。复杂类说明它维护的状态/不变量和由谁提供依赖；无状态工具类不机械凑模板。

```python
"""软米乙方的GET请求和响应协议。

负责字段校验、URL编码和对方响应分类。
调用方负责组织权限、字典映射、交付预占及最终回调记账。
接收成功仅表示乙方收件，不代表易车最终判定有效。
"""
```

Mixin还应声明宿主需提供哪些能力，例如connect、tx、one、audit、_ledger；不要让隐藏依赖只能靠阅读Platform继承顺序猜出来。

## 3. 函数说明：按风险给信息

普通函数1～3句足够。涉及状态、交易、跨系统或权限的公共方法说明以下适用项：

- 目的与主要业务输入；字段属于内部ID还是外部编号。
- 返回结构及“不代表什么”，尤其预览、异步受理、最终结果。
- 权限与组织范围；仅写该方法真实实施的检查，不把调用方检查说成本方法已检查。
- 写库、事务、网络、审计等副作用，是否可重复执行。
- 关键异常/错误码及调用方应如何处理；不罗列每个内部异常。

以下为当前方法可使用的说明示例，签名和行为应与代码同步：

```python
def _matchable_lead_rows(self, conn, actor, buyer_ids=None):
    """逐条返回至少符合一项当前执行需求的线索。

    buyer_ids限定采购主体/项目，未指定时检查当前组织全部执行需求。
    通过共享_block检查配额、售卖限制、授权及品牌车型地区等条件。
    只查询，不预占库存；同一线索即使命中多个需求也只yield一次。
    调用方负责入口权限；创建交付时必须重新校验并原子预占。
    """
```

示例用于说明写法，不要求本次规范任务修改该函数。若未来函数开始写缓存或数据库，必须同步更新“只查询”的描述。

## 4. 业务规则注释

重要分支优先使用“原因＋依据＋边界”，可1～3行，不强制每处完整重复合同背景。详解集中放docs，代码保留能定位的引用。

```python
# 乙方errorCode=1只证明收件成功，不能提前增加最终有效量。
# 依据：docs/软米乙方接口对接说明.md；最终判定等待独立回调。
```

```python
# 预览不持有库存，期间额度可能变化；创建时必须在写事务内再次校验。
```

```python
# 同一最终媒体通过不同乙方交付也受同一去重规则约束。
# 窗口取settings.dedup_window_days，不把当前默认天数写成永久规则。
```

错误示例：`# 每条只能卖两次，行业规定`。本项目上限可配置，也没有据此核实的行业规定。

若已确认规则只针对某个来源/某个编号，注释必须写明范围。例如103171按原表后行处理是已批准的来源级特例，不能描述成“所有重复编号都取最后一行”。

## 5. 状态、事务与回调注释

使用代码中真实字段和枚举。不要发明统一的SENT状态覆盖多个维度：本项目发送状态含QUEUED/ACKED/UNKNOWN/FAILED/CANCELED，媒体入库和有效性另有字段；完整允许值以对应代码为准。

```python
# 先提交唯一发送领取记录，再执行网络I/O，避免持有SQLite写锁等待乙方。
# 请求超时可能已经被对方接收，保持UNKNOWN，不自动重发。
```

```python
# 回调可能先于发送响应到达；已有最终回调时，晚到的响应不能覆盖有效性。
```

```python
# 相同回调只确认接收，不重复冲减在途或增加有效量；矛盾回调保留冲突。
```

注释写“幂等”时说明使用什么唯一键、数据库约束或已处理标记。注释写“原子”时指出同一事务中的哪些变更；不把相邻两次提交称为原子。

## 6. 字段、SQL与迁移

有歧义字段标明业务含义、单位和归属：

```python
# city_id取乙方城市库cityCode，不是字典行id，也不是行政区划代码。
# price_fen单位为人民币分，前端显示时再转换为元。
# callback_at为UTC ISO 8601文本，页面按Asia/Shanghai展示。
```

复杂SQL前说明口径、去重粒度和排除范围。只有核实DDL/查询计划后才声明“命中某索引”；注释里不复制完整表结构。SQL必须参数化，不能用注释宣称已过滤来代替过滤条件。

新迁移头说明目的、兼容性、执行方式与恢复限制。示例中的序号只是后续迁移模板，使用前先核对最新编号：

```sql
-- 目的：增加外部提交查询需要的索引
-- 兼容：只增加索引，不改变现有业务字段
-- 执行：由schema_version控制一次执行
-- 恢复：旧代码可忽略该索引，不删除业务表和数据
```

现有加载器按分号拆分内容，迁移注释内不要写分号。不得给已发布024迁移补注释后重新发布成“新迁移”；说明可放文档或后续版本中。

## 7. 前端注释

说明交互原因、权限边界、异步竞态和状态来源；复杂入口可用简短JSDoc，不给每个DOM节点加注释。

```javascript
// 用户可能在请求完成前切换页面；丢弃旧响应，避免覆盖当前页面。
if (sequence !== renderSequence) return;
```

```javascript
// 隐藏入口只改善操作体验；服务端仍独立校验字段权限。
```

```javascript
/** 将分发详情渲染为只读片段；外部返回文本进入HTML前必须转义。 */
```

不要声称api()会自动执行它尚未实现的行为，例如自动展示全部request_id、全局重试或权限刷新。依赖后端数据计算的数量，应说明统计口径出处，不在前端复制资格规则。

## 8. TODO、临时分支与废弃接口

只有明确待办才使用TODO，格式如下；负责人或期限未确定时如实标注，不能凭空填人名和日期：

```python
# TODO(跟踪=docs/软米乙方接口对接说明.md, 负责人=待分配):
# 增加城市/车系映射管理入口，完成前保持批量推送关闭。
```

临时兼容分支说明触发条件、为何不能立刻删除、移除标准和跟踪位置。有明确期限时补入；过期但仍保留须解释。FIXME用于已证实缺陷，说明影响及证据。不要把真实未完成功能藏在“优化建议”里。

废弃公共接口注明替代方法、仍保留的兼容范围和删除条件。实际删除前核对前端、定时任务、外部调用和测试，不靠注释直接改变行为。

## 9. 注释审查清单

- 与实际代码一致吗？返回、写库、权限与网络副作用有没有说反？
- 依据能找到吗？是否把建议参数写成行业规定，或把示例写成真凭证？
- 组织范围、币种/单位、时区、外部ID与状态维度清楚吗？
- 是否解释了为什么，而不只是重复代码？
- 是否包含手机号、真实姓名、密钥、完整回调令牌或含个人信息的URL？如有，必须移除。
- 变更规则时是否同步修改注释、文档与对应测试？
- 本次只是补注释吗？如改了逻辑，必须单独说明，不能称为“无行为变更”。
